# Rooms, accounts, permissions, friends

Status: design, 2026-11-11. Built in phases so the live group never breaks and old app versions keep working.

## Model

- **users**: one per person: `id, name, color, photo, avatar, friend_code, created_at`. The token identifies a user (`user_tokens`).
- **Photo or drawn avatar**, never both: `PUT /me/photo` clears `avatar`, `PUT /me/avatar {avatar: spec|null}` clears the photo (and deletes its file). A spec is one option index per field of `server/assets/avatar.json`, dot-separated (`0.2.5.1.…`); the server rejects anything else (`bad_avatar`). The parts JSON is generated by `app/scripts/avatar-parts.mjs` (a byte-identical copy in `app/src/lib/avatar-parts.json`), and the app and the share cards draw from it the same way. Both follow the account into every seat (`members.photo` / `members.avatar`). Old apps only read `photo_url` and show the initial.
- **groups** (= rooms): `name, invite_code (rotatable), owner via members.role, settings`.
- **members**: a user in a room: `user_id, group_id, role ('owner' | 'member'), removed_at`. Votes, nudges, pins, skips keep pointing at members, so history is untouched.
- **friends**: `user_id, friend_id`. Anyone you share a room with counts as a friend; a friend code or QR asks someone new (see *Friends and invitations*).

## Requests

- Token = user. Header `X-Room: <group_id>` picks the room; without it, the user's most recently used room (that is what 0.6.x apps do, so they keep working on the main group).
- The `Me` extractor still yields the member for that room, so every existing endpoint stays as is.
- Live socket: one per user, carries events of all their rooms (each event tagged with its room).
- Push: subscriptions move from member to user; a room notification goes to its members' users.

## Migration of the existing group

- Every current member becomes a user (same name, color, photo); `member_tokens` become `user_tokens` with the same hashes, so nobody is signed out.
- Owner of the main group: its earliest member. Ownership can be handed over.
- `JOIN_CODE` (and `GROUP_NAME`) only name the first room when the database is empty; afterwards the owner changes them in the app (a new code from the room settings), restarts don't touch them.

## Rooms and permissions

| Action | Who |
| --- | --- |
| Create a room | anyone (becomes owner) |
| Invite (link, code, QR), invite a friend | any member (owner can restrict) |
| Rotate the invite code | owner |
| Rename, settings | owner |
| Vote to skip / remove | members, if the owner leaves it on, with 3 members or more; the owner can't be voted out |
| Remove someone directly, no vote (force kick) | owner; a removal (vote or owner, not a leave) also deletes the questions they queued that were never asked |
| Delete a chat message | its author; the owner deletes any message of the room (`DELETE /rounds/{id}/messages/{message_id}`) |
| Remove a question already asked | owner (`DELETE /questions/{id}` → `{ok, retired: true}`, or `DELETE /rounds/{id}/question` from its result): the text becomes "Question retirée" / "Question removed" everywhere (history, stats, shares); built-in deck questions can't (`409 deck_question`). Not asked yet: its author or the owner, deleted as before |
| Clear the question queue | owner (`DELETE /questions/queue` → `{deleted}`, `403 owner_only` otherwise, feature `clear_queue`): every upcoming question of the room (what `GET /questions/queue` lists) goes, like `DELETE /questions/{id}` one by one; the deck, questions already asked and the open one stay. Live `question_added` (`question_id: 0`) |
| Unpin a result | whoever pinned it, or the owner (`403 not_pinner`); 100 pins per room at most (`409 too_many_pins`) |
| Hand over ownership, delete the room | owner |
| Leave | anyone; an owner leaving hands over to the oldest member, or deletes the room if alone. The app then opens another of my rooms, or the join / create screen when none is left |
| Come back | someone who left: with the invite code (or an invitation), same seat and history. Someone removed: only with an invitation from the owner |

A majority is more than half of the other members (the target doesn't count), and never one person alone. Whenever an owner seat ends (leaving, removal, account deletion) the oldest remaining member becomes owner; rooms left without one are repaired at startup. People who left stay in `/group` as `former` (flagged `left`) so the history, awards and chat keep their name and photo.

Settings per room: majority skip on/off, majority removal on/off, who can add or import questions (everyone / owner), pacing (below). In the app they live on the owner's "Paramètres du salon" screen (gear on the room page).

## Chat reactions

Feature `chat_reactions`. Any member reacts to a chat message under a finished question with one of ❤️ 😂 😮 😢 👍 🔥 (a bare `❤` counts as `❤️`; anything else `400 bad_emoji`), once per emoji (`message_reactions`, `0039`).

- `POST /messages/{id}/reactions` `{emoji}` adds mine, `DELETE` with the same body takes it back; both idempotent and both answer `{message_id, reactions}`. `404 not_found` for a message of another room, under an open question, hidden by reports, or by someone I blocked.
- Every message (`GET /rounds/{id}/messages`, the `POST` answer) carries `reactions: [{emoji, count, mine, members}]`: emojis in the order above, only those used, `members` oldest first, without the people I blocked.
- A change sends live `message_reacted` `{round_id, message_id}` to the room; no inbox entry, no push.
- Reactions go with their message (deleted by its author, the owner or an admin) and with a deleted account (theirs, and those on their messages). A message hidden by reports keeps them (an admin dismissing the reports shows it back as it was); seats that leave or are removed keep theirs, like their messages.

## Invite preview

`GET /api/rooms/preview?code=` (no account, limited per IP to 30 looks per 10 minutes, feature `room_preview`) is what an invite link shows before joining: `{name, member_count, names}` with up to 3 first names (owner first). No ids, no photos. Unknown codes, deleted rooms and party codes answer `404 bad_code`. The app shows it on the sign-in landing and above the join field; an invite link opened while signed in goes to the room list with the code filled in.

## Pacing

Two owner settings, both off by default (= the next question opens as soon as one closes):

- `owner_next`: only the owner launches the next question (`POST /rooms/{id}/next`, `403 owner_next_off` when off, `409 not_waiting` when nothing waits). Whoever is owner at the time can.
- `next_delay`: seconds to wait after a close (0, 900, 3600, 10800, 43200, 86400).

A paced room that closes a question is *paused* (`groups.paused_at`, `next_open_at` = close + delay, null with no delay): nothing opens it (joins, new questions included) until the owner launches it, the deadline passes, or the owner switches pacing off. Both on: the owner can launch early, else it opens at the deadline. A scheduler task (every 20 s, first run at startup, so restarts lose nothing) opens due rooms and pushes "Nouvelle question". Changing the delay while waiting counts from the close. `GET /group` carries `pace: {waiting, next_open_at, round_id}`; the vote tab keeps that result up with "En attente du propriétaire", a countdown, or the owner's "Lancer la suivante". Older apps just see no open question until it opens.

## When someone is away

Normal rooms have no question timer, so three rules keep them moving when people go quiet (`server/src/flow.rs`, migration `0038_game_flow.sql`; parties have their own, see `docs/PARTY.md`):

- **Away**: someone whose last 3 questions in the room closed without their vote (counting questions that closed since they joined) is *away*: the open question no longer waits for them, like a skip. Voting again makes them present again. The round view lists them in `away_ids` (and leaves them out of `member_count`); the app shows them dimmed with "absent", without a skip button.
- **Late quorum**: a question open for 24 h closes as soon as at least half of the people it waits for voted (2 people: one vote). Checked on each vote and by the scheduler every 5 minutes. This is what gets a 2-person room past a holiday: one question a day, then, after 3, the absent person is away and the room runs at its normal pace.
- **Gone owner**: each seat records when it last used its room (`members.active_at`: any request or live socket for that room, written at most every 10 minutes). An owner unseen for 7 days hands the room to the longest-standing member seen in that time, who gets an inbox entry (`owner`); nobody seen, nothing changes. With `owner_next`, a room waiting for an owner unseen for 24 h (and waiting at least that long) opens its next question by itself.

Also: changing the vibe or the language of an idle room opens a question right away, and the owner hears in the inbox (`ask`: a tap opens the Questions tab) when a question opening leaves only 3 to ask (its own plus the deck's), then when the room runs out (2 people or more, not paced, nothing left to open).

Ballots: a rank or choose ballot leaves with its voter (leaving, removal, account deletion during the question), like the vote. A new ballot from the same seat replaces any older one. Chat messages can carry a `client_key` (up to 64 chars): posting again with the same key returns the message already posted.

## Abuse limits

In-memory token buckets (same limiter as the auth limits in `docs/AUTH.md`, rules in `server/src/quotas.rs`), `429 {"error":"rate_limited","retry_after":s}` with `Retry-After`. The app shows "Trop d'essais, réessaie dans …".

| What | Limit |
| --- | --- |
| Wrong codes: `POST /rooms/join`, signed-in `/join` and `/parties/join`, `POST /friends`, the big screen (`/parties/screen/{code}`, `/live?screen=`) | 10 / hour per account, 20 / 10 min per IP. Only codes that don't exist count (a right code gives its token back), so a party joining from one Wi-Fi is not slowed down |
| Chat messages | 15 / minute and 300 / hour per account |
| Chat reactions (added or taken back) | 60 / minute and 600 / hour per account |
| @mentions | more than 5 people in one message counts as `@tous` and shares its 10-minute cooldown (during it, a plain message for everyone) |
| New rooms and parties | 20 / day per account; 20 rooms owned at a time (`429 too_many_rooms`; a room handed over or deleted frees its place) |
| Room size | 50 people (`409 room_full` on join by code, first-name join, a returning leaver, an invitation sent or accepted); parties: 40 players |
| `POST /rooms/{id}/add` (invitations) | 30 / hour per account |
| Friend requests sent (`POST /friends`, `POST /friends/{id}`) | 30 / hour per account; accepting is free |
| `POST /questions` | 60 / hour per account; `409 question_exists` when the room already has it waiting or was already asked it (built-in deck included) |
| `POST /questions/import` | 10 / hour per account, 500 questions per import (`400 too_many_questions`), 1 MB body |
| `PUT /me/photo` | 10 / hour per account, 12 MB, 8000 px a side at most (decoded off the async threads); stored under a 128-bit random name |
| `POST /push/subscribe` | 30 / hour per account, 10 devices per account (the least recently registered go), Web Push endpoints on a known push service only (below) |
| Live sockets | 8 per account, 64 per IP, 2000 in all (`429 too_many_sockets`); 256-byte messages, only `here` / `away` (anything else closes the socket); a ping every 30 s, closed after 75 s without an answer; every minute the socket checks that its session and seat still exist (closed after a sign-out, a removal or a room deletion; also right after `member_removed` for its own seat and `room_deleted`) |

**What people type** (`server/src/text.rs`): first names, room and party names, pack names and descriptions, questions (added, imported, in packs, suggested), choose items and chat messages lose invisible characters (zero-width spaces, bidi overrides and isolates, word joiners, BOM, soft hyphens, Hangul fillers, blank Braille, control characters; the zero-width joiner stays for emoji). Line breaks and runs of spaces become one space, except in chat messages, which keep their lines with at most one blank line in a row. Nothing visible left: the usual `bad_name` / `bad_room_name` / `bad_question` / `bad_message`. "The same question" compares texts that way and case-insensitively beyond ASCII (`ÉTÉ` = `été`), against the room's own questions and the built-in ones it was already asked; a built-in question the room added by hand is left to that copy (never asked twice).

**Friend codes** are 10 hex digits (40 bits) for accounts made from 0.33; older 8-digit codes keep working. Guessing them is limited like any code (above) and a hit only sends a request.

Push devices belong to the session that registered them (`push_subscriptions.token_hash`, `0030`): signing out, revoking a session, "sign out the others", a password reset or deleting the account removes them (a trigger on `user_tokens`). Devices registered before `0030` stay with the account's only session, or, when it had several, go as soon as any of its sessions ends (the app registers again at its next start). `POST /push/unsubscribe` removes the endpoint from any of my rooms. Web Push endpoints must be https on `fcm.googleapis.com`, `*.push.services.mozilla.com`, `*.push.apple.com` or `*.notify.windows.com` (1 KB at most); stored ones elsewhere are dropped at the next push. Push requests time out after 10 s. FCM tokens are dropped on `UNREGISTERED` / 404, and on `INVALID_ARGUMENT` only when FCM says the token itself is invalid.

## Friends and invitations

Nothing happens to someone without their say (`0031_consent`). Friendships made before stay as they are.

- **Friend request**: `POST /friends {code}` (code or QR) or `POST /friends/{user_id}` (keep a room-mate for good, rooms only, not parties) asks the other person (`friend_requests (from_id, to_id)`): `{user_id, name, status: "requested"}`. If they had already asked me, it accepts instead: two `friends` rows, `status: "friends"`. So `POST /friends/{user_id}` is also how a request is accepted, by anyone who received it. Asking again while it waits does nothing new.
- `GET /friends` → `{code, friends: [{…, added, requested}], incoming: [person], outgoing: [person]}`; `requested` = I asked this room-mate and they haven't answered.
- `DELETE /friends/{user_id}`: removes the friendship, declines their request or cancels mine (everything between us).
- The person asked gets an inbox entry `friend_request` and a push (setting "added to a room") on the room they use most; the app's Friends screen lists the requests to accept or decline.
- **Room invitation**: `POST /rooms/{id}/add {user_id}` (a member, a friend or room-mate, a room not a party: `400 not_a_room`) no longer seats them: it records `room_invites (group_id, user_id, from_id)` and sends an inbox entry `invite` + push. `{invited: true, user_id}`; again while it waits: same answer, no new notice. `409 already_in_room`, `403 not_friends`, `403 owner_only` for someone the owner removed.
- `GET /invites` → `{invites: [{id, room_id, room_name, members, created_at, from: person}]}` (only those still valid: room alive, inviter still in it, no block). `POST /invites/{id}/accept` → `{room_id, member_id}`: a seat (their old one back if they had left; someone removed comes back only if the inviter is the owner, else `403 removed`), the second person in opens the first question; `410 invite_gone` if no longer valid. `DELETE /invites/{id}`: decline (invitee) or take back (inviter).
- `GET /rooms/{id}/invites` → `{user_ids}` pending (members only); `DELETE /rooms/{id}/invites/{user_id}`: the inviter or the owner takes one back.
- Blocking deletes requests and invitations between the two; deleting an account deletes its own.
- **Older apps** (without the `consent` feature): "add by code" and "keep" now send a request (they still say "X est ton ami"; the friend shows up once accepted), "add to room" sends an invitation (the friend isn't seated until they accept from a new app; an old app sees the inbox entry and can join with the room code). Feature flag: `consent` in `/features`.

## Parties

A party (`groups.kind = 'party'`) is a room for an evening in the same place: one question at a time with a countdown, guests without an account, "Suivante" taps. See `docs/PARTY.md`.

## Starting a room

- A room with one active member opens no question: alone, there is nobody to vote for. The app shows an invite screen instead; the first question opens when the second person joins (code, link or "add a friend"), and the others get "Nouvelle question". A question left open when a room drops to one person stays open but can't be voted on (`409 alone`).
- **Vibe**: picked after naming the room (skippable), changeable by the owner. The vibes live in `server/deck/vibes.json` (`GET /vibes`); each one draws built-in deck questions by tag, favourite tag first (`[famille] Qui…` in `server/deck/fr.txt`, untagged = `potes`). No vibe = `potes`, which is what every room had before.
- **Language**: `groups.language` (`fr` | `en`, French by default and for every older room), picked at creation (`POST /rooms {language}`), changeable by the owner (`PATCH /rooms/{id} {language}`, future questions only). The room draws the built-in deck of its language (`server/deck/fr.txt` or `en.txt`); its own questions and installed packs come whatever their language. See `docs/I18N.md`.
- **Out of questions**: the Vote tab offers to write one, install a pack or import a file. When only the owner may add questions, a member can ask them (`POST /questions/ask`: inbox `ask` + push, once per 12 h). Adding one question, installing a pack or importing a file that reopens a stalled room tells the room.

## Phases

1. Server: users, memberships, `X-Room`, migration, push and live per user. No visible change.
2. Server: create / join / leave rooms, invites, owner actions, settings.
3. App: room switcher, create and join screens, group page with invite link and owner settings.
4. Friends: friend code and QR, friend requests to accept, room invitations to accept or decline.
